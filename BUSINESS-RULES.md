## BR-DATA-001 — Routes must refuse material above their data policy [DECIDED]

- RULE: Task material has three classes, from least to most sensitive: `public`, `code` (private project source code and its docs, with no notes, memory, personal or client data, or secrets) and `private` (everything else). Each lane may declare `data_policy: public-only | code-ok | private-ok`: public-only accepts public material, code-ok accepts public and code, private-ok accepts all three. Free promotions default to public-only. Unknown task material defaults to private. Automatic selection, routing and explicit execution must refuse material above the lane's policy: private on public-only and code-ok lanes, code on public-only lanes. Only the operator can approve code-ok or private-ok for a model. Moving a lane to code-ok is the operator's recorded approval for a free model to see private project code (accepting the risk that it lands in training data); it never extends to notes, memory, personal or client data or credentials, which are private. Public classification covers the complete prompt, context, attachments and tool inputs; it cannot grant access to a private workspace. Public-only OpenCode execution therefore uses the existing tool-less `--direct` path. A code-ok lane may read the project workspace the caller points it at, so it does not require `--direct`; the caller is responsible for pointing it at code only.
- Authority: Operator approval is required for per-lane `code-ok` and `private-ok` changes. Existing non-promo lanes default to `private-ok` when the field is absent; newly discovered unverified lanes default to `public-only`. A free OpenCode promo model needs `code-ok` approval to read private project code, and that approval never covers notes, memory, personal or client data, or credentials.
- implemented-by: `scripts/data_policy.py:refusal`, `scripts/fleetctl.py:choose_lane`, `scripts/fleetctl.py:acquire_lease`, `scripts/selector.py:enumerate_options`, `scripts/selector.py:_command`, `scripts/roster.sh:check_lane`, `scripts/opencode-agent.sh:lane_setup`.

- RULE: Agents may change levels, switches, model toggles, model choices and managed pins. They may enable and raise agent-set restrictions. They must not enable a model switched off by the operator or raise a level above the operator's current ceiling. Turning off or lowering is always allowed. A later agent restriction must preserve the operator's ceiling until the operator replaces or releases it. The operator can always change controls, subject to existing model admission and retirement rules.
- Authority: The operator delegates fleet control within the recorded switch and level restrictions. Attribution distinguishes operator changes from agent changes.
- Attribution: console actions and an explicit `--owner` instruction record `owner`; CLI actions otherwise record `agent`. Every control write records time and an optional short reason beside state, with compact append-only history. Unattributed legacy state remains unknown. Console labels latest actor and local time; owner protection is retained separately so an agent cannot erase it by reasserting off.

## BR-VAULT-001 — No external worker writes into the operator's notes [DECIDED]

- RULE: A worker started through any Crossfeed wrapper or dispatch never writes inside the operator's vault (`~/Second Brain/1_Notes`, plus any roots added in `CROSSFEED_PROTECTED_ROOTS`, which can only add). Before launch, refuse (exit 5) a write-capable run whose folder is inside or contains a protected root, an output file (`--last`, `--events`, `--log`) inside one, a Codex config granting one as a writable root, and a brief that names a protected path as a place to put things. Every worker that can use tools starts under a macOS Seatbelt profile that denies file writes under the protected roots, except Codex in its own read-only or workspace-write sandbox (Seatbelt cannot nest; Codex already confines writes to `--dir`). Where the profile cannot be applied (already inside a sandbox, no sandbox-exec while the vault exists), refuse. Reading the vault stays allowed. There is no override: workers deliver into their own folder and the lead files into the vault under its own harness rules.
- Authority: Operator policy enforces the protected-root write boundary regardless of vendor, even if a lead's instructions tell a worker to put outputs in the notes.
